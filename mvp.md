# Функциональные требования к MVP Kanbex

## 1. Цель и границы продукта

MVP — учебный симулятор Kanban-доски для изучения визуализации потока работ и ограничения незавершённой работы (WIP). Пользователь создаёт учётную запись или входит в неё, открывает личную учебную доску, перемещает карточки и получает объяснение правил потока.

В этом MVP входят ASP.NET Core Identity, ASP.NET Core Web API, EF Core Code First и SQLite. 
Состояние доски сохраняется сервером в базе и связано с пользователем. Одна пользовательская сессия не должна видеть или изменять доски другого пользователя.

## 2. Акторы

- **Учащийся** — регистрируется/входит, изучает правила и работает со своей Kanban-доской.
- **Система Kanbex** — аутентифицирует пользователя, отдаёт только его данные, проверяет WIP-ограничения, сохраняет изменения в SQLite и показывает обучающую обратную связь.

## 3. Use case: зарегистрироваться и пройти учебный сценарий на личной доске

### Актор

Новый или существующий учащийся.

### Цель

Получить личную сохранённую учебную доску и на практике понять движение задач по колонкам и действие WIP-лимита.

### Предусловия

1. Приложение доступно в поддерживаемом браузере.
2. Пользователь не вошёл в систему либо имеет действующую ASP.NET Core Identity-сессию.
3. ASP.NET Core API и SQLite доступны.

### Основной сценарий

1. Новый пользователь открывает страницу регистрации, вводит данные учётной записи и отправляет форму.
2. Система проверяет формат и уникальность данных, создаёт пользователя через ASP.NET Core Identity и создаёт аутентифицированную сессию (либо предлагает явно войти, согласно принятому UX).
3. React запрашивает текущего пользователя через API и загружает его список досок.
4. Если учебной доски ещё нет, пользователь создаёт её или система предлагает создать доску с начальными колонками и демонстрационными задачами.
5. React получает доску через Web API и отображает колонки «К выполнению», «В работе» и «Готово», карточки и WIP-лимит.
6. Пользователь перемещает карточку в следующую колонку доступным способом.
7. Клиент отправляет изменение через API; сервер проверяет сессию, право владения доской и WIP-ограничение.
8. При допустимом перемещении сервер сохраняет новое состояние с помощью EF Core в SQLite и возвращает актуальные данные.
9. Интерфейс обновляется и показывает краткое подтверждение или обучающую подсказку.
10. Пользователь выходит или закрывает страницу. После следующего входа система загружает состояние его доски из базы.

### Результат

У пользователя есть личная сохранённая доска; выполненные допустимые перемещения доступны после повторного входа. Учебный сценарий демонстрирует стадии потока и WIP.

### Альтернативные и исключительные сценарии

- **Неверные регистрационные данные:** Identity/API возвращает ошибки валидации, аккаунт не создаётся, форма показывает понятные сообщения.
- **Пользователь уже зарегистрирован:** регистрация отклоняется без раскрытия лишних персональных данных; предлагается войти или восстановить доступ, если соответствующий сценарий включён.
- **Неверный логин/пароль:** вход отклоняется, доски не выдаются, пользователь остаётся на форме входа.
- **Неаутентифицированный запрос к личной доске/API:** API возвращает `401 Unauthorized`; UI предлагает войти.
- **Попытка изменить чужую доску:** сервер не раскрывает данные и возвращает `404 Not Found` либо согласованный `403 Forbidden`; изменение не сохраняется.
- **WIP-лимит достигнут:** API отклоняет перенос с подходящим кодом/ошибкой предметной области, UI объясняет, почему нужно завершить или переместить существующую работу.
- **Конфликт изменения:** если доска была изменена параллельно, сервер возвращает актуальное состояние или конфликт, клиент предлагает обновить данные; полноценное realtime-согласование не требуется.
- **Ошибка сети/БД:** пользователь видит сообщение и возможность повторить запрос; UI не показывает несохранённое изменение как подтверждённое.
- **Drag-and-drop недоступен:** карточку можно переместить кнопкой или меню; управление мышью не является единственным способом.
- **Сброс учебной доски:** пользователь подтверждает сброс; система восстанавливает начальные данные только для его доски.

## 4. Функциональные требования MVP

### 4.1. Учётные записи и доступ

1. Поддержать регистрацию, вход и выход с использованием ASP.NET Core Identity.
2. Хранить пароль только средствами Identity в виде безопасного хэша; не возвращать пароль, хэш и служебные секреты через API.
3. Использовать same-origin cookie-аутентификацию для MVC и Web API.
4. Личные маршруты и API требуют аутентификации.
5. Сервер проверяет владельца доски при каждой операции чтения и изменения; клиентские проверки не считаются контролем доступа.
6. Обеспечить защиту изменяющих состояние запросов от CSRF.
7. Восстановление пароля, подтверждение e-mail, внешние провайдеры входа и роли администратора могут быть исключены из MVP, если для учебной демонстрации не требуются.

### 4.2. Доски и API

1. Пользователь может получить список только своих досок и создать как минимум одну учебную доску.
2. Новая доска содержит начальные колонки «К выполнению», «В работе», «Готово» и демонстрационные карточки.
3. Web API предоставляет операции для текущего пользователя: чтение списка и доски, создание доски, изменение порядка/положения карточки и сброс учебной доски.
4. API использует отдельные DTO; EF Core-сущности и Identity-модели не возвращаются напрямую.
5. Ошибки валидации, отсутствия сессии, отсутствия ресурса, нарушения WIP и серверной ошибки возвращаются предсказуемо и отображаются в интерфейсе.

### 4.3. Колонки, карточки и WIP

1. Отображать название доски, колонки, карточки и количество задач.
2. Показывать WIP-лимит для ограниченных колонок.
3. Позволять перемещать карточку между этапами; поддержать drag-and-drop и доступную альтернативу с клавиатуры/кнопки/меню.
4. Сервер является источником истины: допустимое перемещение сохраняется через API и SQLite.
5. Не допускать превышения WIP-лимита; UI отображает объяснение причины.
6. Позволять открыть карточку и посмотреть заголовок и краткое описание.
7. Сброс демонстрационной доски требует подтверждения и сохраняется на сервере.

### 4.4. Обучение и UX

1. Объяснять назначение колонок и базовую идею движения работы.
2. Давать краткую контекстную обратную связь после успешного перемещения.
3. Объяснять WIP-ограничение при отклонённом действии.
4. Показывать состояния загрузки, пустой список досок и ошибки API.
5. Адаптировать доску к узкому экрану; допускается горизонтальная прокрутка колонок.
6. Основные действия должны быть доступны с клавиатуры и иметь понятные подписи.
7. Использовать общие компоненты `Kanbex.UI` и тему/компоненты `m3-expressive-react`.

### 4.5. Сохранение и схема БД

1. Хранить Identity-пользователей, доски, колонки и карточки в SQLite через Entity Framework Core.
2. Разрабатывать модель по Code First; схему создавать и изменять только через EF Core Migrations.
3. Сохранять изменения доски на сервере; браузерное `localStorage` не является основным хранилищем личных данных.
4. Установить связь владельца между доской и пользователем, а также целостные связи доски/колонок/карточек.
5. Предусмотреть начальное создание учебного содержимого для нового пользователя или явную команду создания демо-доски.
6. Проверять миграции на чистой SQLite-БД и на обновлении с предыдущей версии схемы.

## 5. В границах MVP

- ASP.NET Core MVC-хост на C# и React-интерфейс через Vite/ViteDotNet.
- ASP.NET Core Web API для сессии и операций с досками.
- ASP.NET Core Identity: регистрация, вход, выход и авторизованные личные данные.
- EF Core Code First, EF Core Migrations и SQLite.
- Личный список и минимум одна сохранённая учебная доска для пользователя.
- Начальные колонки/задачи, карточки, WIP-лимит и перенос задач.
- Проверки доступа владельца на сервере.
- Обучающие подсказки, обработка ошибок/загрузки, адаптивность и базовая доступность.
- Unit-/интеграционные проверки критических сценариев: Identity, API авторизации, доступ к своей/чужой доске, WIP и сохранение.

## 6. Вне MVP

- Совместная работа, приглашения, команды, роли и совместное редактирование в реальном времени.
- PostgreSQL, SQL Server или другая серверная СУБД; SQLite — единственная БД первого MVP.
- Отчёты, аналитика, диаграммы потока, cycle time/lead time и прогнозирование.
- Полноценный конструктор workflow, сложные правила, автоматизация и интеграции.
- Комментарии, файлы, уведомления и аудит действий.
- Восстановление пароля/e-mail, OAuth/внешние провайдеры и многофакторная аутентификация, если не будут отдельно признаны обязательными.
- Мобильные нативные приложения, offline-first режим и синхронизация локальных изменений.
- Многоарендность и административная панель.

## 7. Критерии приёмки MVP

1. Новый пользователь может зарегистрироваться, войти и выйти; ошибки учётных данных отображаются безопасно и понятно.
2. Неаутентифицированный пользователь не может получить или изменить личную доску через API.
3. Пользователь может создать и открыть собственную учебную доску с тремя этапами и несколькими карточками.
4. Пользователь может перемещать карточки; поддерживаются доступная альтернатива drag-and-drop и обновление интерфейса после ответа сервера.
5. WIP-ограничение проверяется сервером; превышение не записывается и сопровождается понятным сообщением.
6. Пользователь не может получить или изменить доску другого пользователя; это проверено автоматическим API-/интеграционным тестом.
7. После выхода и повторного входа допустимые изменения доски сохранены в SQLite.
8. Схема базы может быть создана на чистом файле SQLite миграциями EF Core и обновлена очередной миграцией.
9. Сбой API/БД не приводит к отображению неподтверждённого изменения как сохранённого.
10. MVC/Razor и React-бандлы работают в Development и Production.

## 8. Технологические и безопасностные допущения

- SQLite — локальная база MVP, не предназначенная сама по себе для конкурентного production-развёртывания с высокой нагрузкой.
- API и React обслуживаются с одного origin; cookies настраиваются с подходящими `HttpOnly`, `Secure` в HTTPS и `SameSite` атрибутами.
- Секреты и строка подключения для развёртывания задаются через конфигурацию окружения/секрет-хранилище; чувствительные значения не коммитятся.
- Сервер повторно проверяет правила доступа и WIP; валидация только на клиенте недостаточна.
- Выход из аккаунта и все изменяющие запросы защищаются подходящими antiforgery/CSRF-мерами для выбранного cookie-flow.
- Идентификаторы, ошибки и ответы API не должны раскрывать данные чужих досок или внутренние детали Identity.

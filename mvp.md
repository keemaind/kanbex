# Kanbex — функциональные требования к MVP

**Версия:** 0.2.0

## 1. Назначение

Kanbex — учебный симулятор Kanban-потока. Пользователь ведёт доски с колонками, карточками, приоритетами и WIP-лимитами и на практике видит, как ограничение незавершённой работы влияет на движение задач.

MVP включает ASP.NET Core MVC/Web API, ASP.NET Core Identity, EF Core Code First, EF Core Migrations и SQLite. Состояние досок хранится на сервере и привязано к пользователям и их ролям в проекте.

## 2. Акторы и роли

- **Гость** — неаутентифицированный посетитель. Видит публичные страницы и публичные read-only доски.
- **Пользователь** — аутентифицированный учащийся. Работает со своими досками и досками, где он участник.
- **Администратор** — пользователь с глобальной ролью `Admin`. Управляет пользователями и глобальными ролями через `/admin/users`.

Роли в проекте:

- **Creator** — владелец доски: участники, видимость, сброс, удаление и полный доступ к содержимому.
- **Member** — участник: читает и редактирует карточки, колонки, комментарии и теги, читает историю; не управляет участниками, видимостью, сбросом и удалением доски.

| Действие | Гость | User (не участник) | Member | Creator | Admin |
|---|---|---|---|---|---|
| Публичная read-only доска | да | да | да | да | да |
| Приватная доска | нет | нет | да | да | нет |
| Задачи, колонки, комментарии, теги | нет | нет | да | да | нет |
| Настройки, сброс, удаление, участники, видимость | нет | нет | нет | да | нет |
| `/admin/users` и глобальные роли | нет | нет | нет | нет | да |

## 3. Use case UC-1. Регистрация и работа с личной Kanban-доской

### Актор

Гость или Пользователь.

### Цель

Получить личную сохранённую доску и на практике увидеть движение задач по этапам и действие WIP-лимита.

### Предусловия

1. Приложение доступно в поддерживаемом браузере.
2. Пользователь не аутентифицирован либо имеет действующую cookie-сессию.
3. ASP.NET Core API и SQLite доступны.

### Основной сценарий

1. Пользователь открывает `/register` или `/login` и вводит данные.
2. ASP.NET Core Identity проверяет формат и уникальность, создаёт пользователя и cookie-сессию.
3. React загружает текущего пользователя и список доступных досок.
4. Пользователь создаёт доску с нуля или по шаблону: `student`, `developer`, `manager`, `personal`.
5. Доска открывается с колонками (по умолчанию «К выполнению», «В работе», «Готово»), карточками и WIP-лимитом.
6. Пользователь перемещает карточку drag-and-drop; клавиатурное управление обеспечивает `KeyboardSensor` из `@dnd-kit`.
7. Клиент отправляет изменение через API; сервер проверяет сессию, участие в проекте, версию доски и WIP-лимит.
8. Сервер сохраняет изменение через EF Core в SQLite и возвращает актуальную доску.
9. Интерфейс обновляется и показывает подтверждение либо объяснение отказа.
10. Пользователь открывает карточку, меняет исполнителя, дедлайн и оценку, добавляет комментарий и теги; история фиксирует изменения.
11. Пользователь выходит; после повторного входа состояние доски восстанавливается.

### Результат

У пользователя есть личная сохранённая доска. Допустимые перемещения и изменения сохраняются в SQLite и доступны после повторного входа. Пользователь видит стадии потока и ограничение WIP.

### Альтернативные сценарии

- **Неверные регистрационные данные:** Identity возвращает ошибки валидации, аккаунт не создаётся.
- **E-mail уже зарегистрирован:** регистрация отклоняется без раскрытия лишних данных.
- **Неверный логин или пароль:** вход отклоняется, сессия не создаётся.
- **Неаутентифицированный запрос к API:** `401`; UI предлагает войти.
- **Чужая или приватная доска:** `404` без раскрытия существования.
- **WIP-лимит достигнут:** сервер не сохраняет перемещение и объясняет причину.
- **Конфликт версии:** `409`; клиент предлагает загрузить актуальную доску или сохранить поверх.
- **Ошибка API/БД:** показывается явная ошибка; несохранённое изменение не выглядит сохранённым.
- **Drag-and-drop недоступен:** перемещение доступно с клавиатуры; отдельные кнопки не требуются.
- **Исполнитель не участник доски:** сервер отклоняет изменение.
- **Некорректный комментарий или тег:** `400` с понятным сообщением.
- **Сброс доски:** требуется подтверждение; восстанавливается начальный учебный набор.
- **Некорректный аватар:** неподдерживаемый тип или размер больше 2 МБ отклоняется.

## 4. Use case UC-2. Совместная работа на доске

### Актор

Creator и Member.

### Предусловия

Creator аутентифицирован и владеет доской; приглашаемый пользователь зарегистрирован.

### Основной сценарий

1. Creator открывает список участников доски.
2. Добавляет пользователя по e-mail с ролью `Member`.
3. Member видит доску в списке доступных и открывает её.
4. Member редактирует карточки, колонки, комментарии и теги, читает историю.
5. Creator видит изменения; участники не мешают друг другу.
6. Member не может менять участников, видимость, настройки, сбрасывать и удалять доску.

### Результат

Доска доступна нескольким пользователям с разделением прав Creator/Member.

### Альтернативные сценарии

- Неизвестный e-mail — `400`/`404` без создания участника.
- Повторное добавление — дубликат не создаётся.
- Попытка добавить владельца или себя — отклоняется.
- Member пытается выполнить Creator-only действие — `403`.
- Creator удаляет Member — доступ прекращается сразу.

## 5. Use case UC-3. Публичная read-only доска

### Актор

Creator и Гость.

### Предусловия

Creator владеет доской; публичность по умолчанию выключена.

### Основной сценарий

1. Creator открывает настройки публикации.
2. Включает `IsPublic` и копирует ссылку `/share/{boardId}`.
3. Гость открывает ссылку без входа.
4. Гость видит колонки, карточки, теги, приоритеты и имена исполнителей.
5. Гость не может редактировать доску, карточки и комментарии.
6. Creator выключает публичность; ссылка перестаёт работать.

### Результат

Доска доступна анонимно только для чтения, без персональных данных владельца и участников.

### Альтернативные сценарии

- Приватная или несуществующая доска — одинаковый `404`.
- Изменяющий запрос от гостя — `401`.
- Публичный ответ не содержит e-mail, участников, комментариев и истории.

## 6. Use case UC-4. Администрирование пользователей и ролей

### Актор

Администратор.

### Предусловия

Пользователь аутентифицирован и имеет глобальную роль `Admin`.

### Основной сценарий

1. Администратор открывает `/admin/users`.
2. Ищет пользователей, фильтрует по роли и листает страницы через query string.
3. Меняет глобальную роль пользователя.
4. Обновляется security stamp; новые права применяются.
5. Система не позволяет снять `Admin` с себя или удалить последнего администратора.

### Результат

Глобальная роль изменена, доступ пользователя обновлён.

### Альтернативные сценарии

- Анонимный пользователь — редирект на `/login`.
- Пользователь без роли `Admin` — `/access-denied`.
- Попытка снять последнего админа — ошибка валидации.
- Неизвестная роль — `400`.

## 7. Функциональные требования по областям

### 7.1. Учётные записи и доступ

- Регистрация, вход и выход через Identity; пароли хранятся только в виде хэша.
- Same-origin cookie-аутентификация `Kanbex.Auth`; изменяющие запросы защищены antiforgery.
- Личные страницы и API требуют аутентификации; публичные страницы и публичные доски доступны анонимно.
- Сервер проверяет участие в проекте при каждом чтении и изменении.
- Глобальные роли `User`/`Admin`; роли проекта `Creator`/`Member`.

### 7.2. Доски и карточки

- Список доступных досок, создание с нуля и по шаблонам.
- Три начальные колонки, демонстрационные карточки, WIP-лимит.
- Drag-and-drop с клавиатурной поддержкой; сервер проверяет WIP и версию.
- Исполнитель, дедлайн и оценка карточки; исполнитель — только Creator/Member.
- Комментарии, теги и история задачи.
- Сброс и удаление доски — только Creator.

### 7.3. Совместная работа

- Creator добавляет/удаляет Member по e-mail.
- Member редактирует содержимое, но не управляет доской.
- Список досок включает доски, где пользователь Member.

### 7.4. Публичная доска

- `IsPublic` по умолчанию выключен; переключает только Creator.
- Отдельный read-only endpoint и DTO без персональных данных.
- Ссылка `/share/{boardId}` доступна анонимно; мутации запрещены.

### 7.5. Аватар

- Пользователь загружает, заменяет и удаляет свой аватар.
- JPEG/PNG/WebP до 2 МБ; хранение в `wwwroot/uploads/avatars/{userId}/`.
- `AvatarUrl` возвращается в `/api/auth/me`; инициалы — fallback.

### 7.6. Админка и механизмы

- `/admin/users`: поиск, фильтр, пагинация, смена глобальной роли.
- Сессии, `IMemoryCache`, cookie `kanbex.admin.last-search`, singleton `AppState`, query string.
- Атрибуты валидации и `ModelState` на MVC-странице.

### 7.7. Данные и EF Core

- EF Core Code First, миграции и SQLite.
- Существующие таблицы `Comments`, `Tags`, `TaskTags`, `TaskHistory`, `ProjectMembers` используются без новых таблиц.
- Ограничения: карточка — заголовок до 200, описание до 10000; комментарий — 1–4000; тег — имя до 64, цвет `#RRGGBB`; оценка — целое `>= 0`; имя проекта — до 120.
- Миграции проверяются на чистой базе и на обновлении с предыдущей версии.

## 8. Границы MVP

### 8.1. Входит в MVP

- ASP.NET Core MVC-хост, Razor-страницы и React-клиент через Vite/ViteDotNet.
- ASP.NET Core Web API для сессии, досок, участников, комментариев, тегов, истории и админки.
- Identity: регистрация, вход, выход, глобальные роли `User`/`Admin`.
- Роли проекта `Creator`/`Member` и проверка доступа к доске.
- EF Core Code First, миграции и SQLite.
- Личный список досок, шаблоны, колонки, карточки, WIP и перенос задач.
- Исполнитель, дедлайн и оценка карточки.
- Комментарии, теги и история задачи.
- Участники проекта и публичная read-only доска.
- Серверное хранение аватара.
- Сессии, Application-состояние, кэш, cookies и query string.
- Адаптивность, состояния загрузки/пустоты/ошибок и понятные подписи.

### 8.2. Не входит в MVP

- Realtime-совместное редактирование, отправка приглашений по e-mail, команды и общие пространства.
- Передача владения доской и несколько Creator у одной доски.
- Файлы и вложения к задачам, уведомления, общий аудит действий (кроме истории задачи и смены глобальных ролей).
- PostgreSQL/SQL Server; SQLite — единственная БД MVP.
- Отчёты, аналитика, cycle time/lead time и прогнозирование.
- Полноценный конструктор workflow, автоматизация и интеграции.
- Восстановление пароля, подтверждение e-mail, OAuth и MFA.
- Мобильные приложения, offline-first и синхронизация.
- Многоарендность и административная панель шире `/admin/users`.
- Отдельные кнопки перемещения карточек и отдельная панель обучающих подсказок.

## 9. Ограничения и допущения

- SQLite — локальная БД MVP, не рассчитанная на высокую конкурентную нагрузку.
- API и React работают на одном origin; cookies `HttpOnly`, `SameSite`, `Secure` при HTTPS.
- Секреты и строки подключения задаются конфигурацией окружения.
- Сервер повторно проверяет доступ и WIP; клиентская валидация не заменяет серверную.
- Публичная доска отдаёт минимум данных: без e-mail, участников, комментариев и истории.
- Демо-учётки создаются только в Development; загруженные аватары не попадают в git.

## 10. Критерии готовности MVP

1. Новый пользователь регистрируется, входит и выходит; ошибки учётных данных понятны.
2. Анонимный пользователь не получает приватную доску; публичная доска доступна read-only.
3. Пользователь создаёт и открывает доску с тремя этапами и карточками.
4. Карточки перемещаются drag-and-drop с клавиатурной поддержкой; WIP проверяется сервером.
5. Исполнитель, дедлайн и оценка сохраняются; чужой исполнитель отклоняется.
6. Комментарии и теги работают с проверкой прав и ограничений.
7. История фиксирует создание, изменение, перемещение и назначение.
8. Creator управляет участниками; Member редактирует содержимое, но не доску.
9. Публичная ссылка работает анонимно и не раскрывает персональные данные.
10. Аватар загружается, заменяется и удаляется через сервер.
11. Администратор управляет глобальными ролями; последнего админа снять нельзя.
12. Схема создаётся на чистой SQLite миграциями и обновляется с предыдущей версии.
13. Сбой API/БД не выглядит как сохранённое изменение.
14. MVC/Razor и React-бандлы работают в Development и Production.
